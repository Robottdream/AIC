# 导航位姿停更：TF 异步等待死锁修复

## 根因证据

2026-09-30，关闭看门狗自动重启后保留故障进程，记录原始 `/tf`、`/navigation/tf`、`/clock` 和局部/全局地图足迹；TF 同时使用可靠与尽力 QoS 观察。上游持续更新，局部地图足迹仍按 10 Hz 发布，但位姿时间戳落后 8.198 s，并继续增长。说明不是所有上游消息停发，也不能由足迹时间戳断言节点时钟冻结。

GDB 捕获 controller_server PID 46764：

| 线程 | 正在等待 | 已持有 |
| --- | --- | --- |
| 46977，雷达回调，经 waitForTransform → addTransformableRequest | BufferCore 请求锁，地址 0x5a21a25c8c30 | Buffer 定时器登记锁，地址 0x5a21a25c8ce0 |
| 46967，TF 回调，经 setTransform → testTransformableRequests → 完成回调 | Buffer 定时器登记锁，地址 0x5a21a25c8ce0 | BufferCore 请求锁，地址 0x5a21a25c8c30 |

现场读取 pthread mutex 的 owner，两个地址分别返回 46967、46977，与上述栈吻合。地图更新线程仍能查询缓存中的旧变换，因而发布旧位姿；负责加入新变换的线程已经锁死。证据在 `/mnt/e/workspace/AIC/log/tf-root-20260930/live.jsonl`、controller-bt.txt 和 mutex-owners.txt。

本机安装 tf2_ros **0.25.23**、Nav2 **1.1.20**。对应源码中 waitForTransform 在定时器登记锁内调用 addTransformableRequest，而 BufferCore 在请求锁内调用完成回调，该回调再取定时器锁，形成反向锁顺序。依据：[Buffer](https://github.com/ros2/geometry2/blob/0.25.23/tf2_ros/src/buffer.cpp)、[BufferCore](https://github.com/ros2/geometry2/blob/0.25.23/tf2/src/buffer_core.cpp)。

## 实现

新增 `src/aic_tf2_fix`，只替换上述异步等待函数：登记 BufferCore 请求时不持有定时器登记锁；若变换在请求登记结束前到达，用独立请求状态记录完成结果，登记好超时定时器后再完成。保留超时、不可变换、立即成功的处理。

编译和启动都限定 tf2_ros 0.25.23，避免 ROS 升级后静默加载未验证 ABI。导航 launch 在自己的进程组作用域内设置 LD_PRELOAD，现场 `/proc/<pid>/maps` 已确认 planner_server、controller_server 加载修复库。没有修改 `/opt/ros`、伪造 TF 时间戳或绕过速度保护；依赖使用本机已有 ROS 开发库，第三方 BSD 说明随包保存。

同时修正主控选块定位来源：静态 identity map→odom 模式下订阅 `/odom`，与 Nav2 坐标一致；AMCL 模式仍订阅 `/amcl_pose`。避免未参与导航的 AMCL 估计漂移污染候选路径起点。任务执行顺序保持原样。

## 验证

`tools/check_tf_async_fix.py` 对同一个 C++ 并发探针作原库/修复库对照。20,000 个异步等待与另一个线程持续到达的 TF 竞争，随后验证超时和立即成功：

| --- | --- | --- |
| 安装原库 | 卡住，15 s 超时强制结束 | 15.02 s |
| 修复库第 1 轮 | 20,001 次成功（含立即成功）、1 次预期超时 | 4.08 s |
| 修复库第 2 轮 | 同上 | 4.27 s |
| 修复库第 3 轮 | 同上 | 4.14 s |

报告为 `/mnt/e/workspace/AIC/log/tf-root-20260930/stress-check.json`。选择构建 aic_tf2_fix、bot_navigation、main_controller 均成功；一键 headless 冷启动就绪门与体检通过。

### 额外捕获的移动障碍互堵

第五件已抓住 blue_cube_4，但在前往旧引导点 (-7,-4.3) 的路上，被移动障碍 2 堵住。故障时扫描在近障停车区内有约 40 束回波，实际障碍 2 在 (-8.061,-3.963) 附近、速度接近零且仍试图返回 (-9,-4.2)。小车在 (-8.718,-3.738) 附近，两者相互阻挡。控制器重复提示 collision ahead，当前地图位姿仍更新；这是另外的路径/相遇问题。

将 blue_cube_4→C 的返程引导点改到北侧 (-7,-2.4)，先离开抓取区再前往 C，保留碰撞与雷达保护。第二次一键冷启动后先导航到 C 停车点，再通过自然语言重跑该物块，**53.835 s 成功**，三个任务导航目标均 succeeded。物块 Gazebo 坐标 (-6.702,-7.593,0.750)，中心在 C 区范围内；本轮 IMU 最大倾角 0.027°。只验证了一次相遇，不能保证不同障碍相位都不互堵。

同一场景接着重跑“抓取1个红色去B”，选择 red_cube_4，**57.306 s 成功**，零导航恢复；物块坐标 (-1.025,-6.308,0.750)，中心在 B 区范围内。该任务从 C 出发，接近方向与之前失败现场不同，不能把 202.84→57.31 s 当作严格同条件成绩对比。

第二场景同时监测 240 s：448 个有效样本，位姿过期样本 **0**，最大局部/全局滞后 0.217 / 0.243 s；看门狗没有重启导航。报告在 c-route-endurance、c-route、red-b 子目录。两次冷启动分别完成了六种任务类型的验证，首轮并非六件连续成功。

任务后的 120.025 s 专门空闲监测完成：221 个有效样本，位姿过期样本 **0**；最大局部/全局滞后 0.125 / 0.219 s，时钟接收最大停顿 0.108 s。结果在 idle 子目录。

## 边界

此修复针对已捕获的异步 TF 锁死，不保证所有导航失败、墙角或动态障碍问题消失。短时 TF 等待仍可能发生，已有失联停车及任务接续保护继续保留。ROS 升级后必须重新审阅兼容修复；不要直接拿旧库用于其他 tf2_ros 版本。
