# 比赛展示布局

导入文件：根目录 `foxglove_competition_layout.json`。

## 导入与使用

1. 在 Foxglove 的布局菜单选择“从文件导入”，选择该 JSON。
2. 使用 Rosbridge 连接 `ws://127.0.0.1:8765`，在新任务发令前导入布局。
3. 在上方“题目与映射规则”面板的 `data` 中粘贴完整新题目，
   包括题末 x、y 的定义。末尾可填写 `映射规则：1`（或裁判指定的 2、3），
   也可粘贴三条正式映射规则中所选规则的完整文字。
4. 点击“解析新题目”。检查上方接收原文、四张数量/区域卡和右侧答案预览。
5. 从本次预览复制 `preview_id`，填入右下“开始任务”面板消息中的同名字段，
   核对后点击“核对后开始任务”。

输入框默认空白，没有预填书箱题；导入布局不会发令或启动小车。
题目发布消息类型为 `std_msgs/msg/String`，格式如下，占位内容要换成完整题目：

```json
{"data":"完整新题目，包括x、y的定义。\n映射规则：1"}
```

确认面板格式如下，编号使用当前预览中的实际值：

```json
{"data":"{\"preview_id\":\"本次预览编号\",\"confirm\":true}"}
```

新一轮测试需要恢复货物位置时，使用现有 `restart --headless` 入口。

## 面板及数据

- 上方：可编辑题目/规则、已接收原题/规则/解析状态。
- 第二行：红色数量、蓝色数量、蓝色放置区域、红色放置区域。
  数量来自实际预览/执行任务，同色多区域会同时列出；错误预览清除旧结果。
- 左下：彩色相机、深度相机、三维地图/小车/雷达，沿用原布局的有效配置。
- 右侧：当前第几个、当前任务、实际抓取/释放状态、已确认放置数、
  完整解题预览、核对后的启动按钮。

JSON 内嵌 Foxglove User Script，将已有 ROS 消息转为展示字段，无需安装扩展或修改 ROS 节点。
原有 `demo1.json` 保留。

状态来自 `/task_stage`、`/competition/ready`、`/arm_status` 和 `/current_target_cube`。
只有实际 `place_succeeded` 才增加已放置数，同一物块重复消息去重。
进入 PLACE 或 `/pick` 的提前状态不当作已释放；失败放置不计完成。
脚本只转换消息，不发布机器人命令；启动仍须本次预览编号和明确确认。

运行中途导入时，脚本无法恢复接入前的放置次数；进度显示“等待新任务/等待确认”，
当前任务仍按实时状态显示。先导入再发令，可以统计完整一轮。
本布局不是计时器，也不自动生成正式题目。

## 礼品盒题解析修复

2026-10-18 用户截图中的礼品盒题已到达 `/competition/problem`，
旧后端只接受衣柜/书箱容量与四个固定物品名称，因而在容量识别处拒绝。
旧后端也未处理完整文字映射规则，只识别末尾编号。

现在支持衣柜、书箱、礼品盒/礼盒的容量描述，从题末容器数量的 x、y 定义提取物品，
支持件/条/本/个/颗/粒单位，保留重复人物、未知需求物品、负数、小数和循环参照检查。
三条正式文字规则均可识别；无法识别的映射文字、编号与文字冲突会明确报错。
这仍是容器需求题的结构化求解器，并非任意数学题的通用求解器。

本次礼品盒样例：软糖总需求 17、硬糖总需求 4，每盒 5 个，x=4、y=1；
规则 1 映射为 4 红到 A、1 蓝到 C。改变需求数量、物品名称、变量定义或规则后分别计算，
不使用固定任务。17 项解析/确认测试、全套 63 项 Python 测试通过。
仅构建 `llama_command_parser` 包，更新当前暂存工作区并重启其解析节点；其他进程保留。
隔离 ROS 域使用实际解析节点和现有 llama-server 完成预览验证，大模型映射一致，
`/chat` 发布数为 0，没有启动搬运。证据见忽略提交的 `log/gift-parser-20261018/`。
随后只读核查当前运行域：实际题目预览 `300e5dc37e01` 同样为 x=4、y=1，
映射为 4 红到 A、1 蓝到 C，大模型映射一致；状态已变为 started，主控正在执行。
本次工具未向运行域发布题目或启动消息；这项状态核查不代表搬运已完成。
现有 Foxglove 布局无需重新导入；下一道题重新解析后使用其新的预览编号。
